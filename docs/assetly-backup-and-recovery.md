# Assetly DB 백업·복원 운영 가이드

기준일: 2026-10-11

## 1. 현재 범위

Compose의 PostgreSQL을 custom-format 아카이브로 백업하고, 동일한 PostgreSQL 서비스의 **새 DB**에 복원하는 도구를 제공한다. 기존 운영 DB 덮어쓰기, 자동 운영 전환과 DB 삭제 기능은 제공하지 않는다.

- 백업 CLI: `scripts/database-backup.mjs backup`
- 복원 CLI: `scripts/database-backup.mjs restore`
- 안전성 테스트: `scripts/database-backup.test.mjs`
- 실제 PostgreSQL 복원 검증: `scripts/verify-database-backup.mjs` (격리된 CI 전용)

실행에는 Node.js 22 이상, Docker 엔진, Docker Compose와 실행 중인 `postgres` 서비스가 필요하다. 프로젝트 루트에서 실행한다. PostgreSQL 클라이언트 도구는 컨테이너 내부의 것을 사용하므로 호스트에 따로 설치하지 않는다.

서버·도메인은 아직 미정이다. 도구와 CI 검증을 구성한 것이며, 운영 서버 정기 스케줄·외부 백업 저장소·재해 복구 전환은 아직 설정하지 않았다.

## 2. 백업

```powershell
node scripts/database-backup.mjs backup
```

기본 저장 위치는 현재 작업 디렉터리의 `backups/assetly-시각-임의값.dump`이다. 원하는 경로를 명시할 수도 있다.

```powershell
node scripts/database-backup.mjs backup --output backups/manual-check.dump
```

동작:

1. 현재 Compose 프로젝트의 실행 중인 PostgreSQL 컨테이너를 확인한다.
2. 컨테이너의 `POSTGRES_DB`와 `POSTGRES_USER`를 이용해 `pg_dump --format=custom`을 실행한다.
3. 바이너리를 Node.js 스트림으로 임시 파일에 저장한다. PowerShell의 텍스트 리다이렉션에 의존하지 않는다.
4. 정상 종료와 custom-format 헤더를 확인한 뒤 완성 파일을 게시한다.
5. 기존 파일 덮어쓰기를 거부하고 실패 시 임시 파일을 정리한다.

파일 게시에는 같은 파일시스템의 hard link를 사용한다. 해당 기능을 지원하는 로컬 디스크에 먼저 저장하고, 완성된 파일을 외부 저장소로 전송한다. 출력 디렉터리에 쓸 권한이 없거나 hard link를 지원하지 않으면 백업은 실패 처리된다. 성공 로그 없이 파일이 만들어졌다는 이유만으로 백업 성공으로 판단하지 않는다.

프로세스 강제 종료·정전은 `.partial` 파일을 남길 수 있다. 이를 정상 백업으로 취급하지 않고, 실행 중인 백업이 없는지 확인한 뒤 정리한다.

백업은 한 DB의 스키마, 데이터, 시퀀스와 Flyway 기록을 포함한다. 클러스터의 역할·테이블스페이스, `.env`, JWT 비밀값, 서버 설정과 향후 외부 파일 저장소는 포함하지 않는다. 복원에는 별도로 준비한 DB 계정과 환경 설정이 필요하다.

## 3. 별도 DB 복원

신뢰할 수 있는 직접 생성한 백업만 사용한다. PostgreSQL 백업 복원은 SQL을 실행하므로 출처를 알 수 없는 파일을 운영 클러스터에서 복원하지 않는다.

```powershell
node scripts/database-backup.mjs restore --file backups/manual-check.dump --database assetly_restore_check_20261011
```

복원 대상 이름은 `assetly_restore_` 뒤에 소문자·숫자·밑줄 1~40자를 붙인다.

안전장치:

- 파일 형식과 아카이브 목록을 먼저 검사한다.
- `createdb`로 새 DB를 만든다. 이미 존재하는 이름이면 복원을 중단한다.
- 기존 DB를 삭제·초기화하거나 `--clean`으로 덮어쓰지 않는다.
- 원본 DB의 데이터나 앱의 연결 설정을 변경하지 않는다.
- 소유자·권한을 원본 그대로 적용하지 않고 복원 계정 기준으로 복원한다.
- `pg_restore --single-transaction --exit-on-error`로 중간 실패 시 데이터 적용을 롤백한다.
- 실패 시 새로 생성한 DB는 진단을 위해 남긴다. 기존 DB 이름으로 재시도할 수 없으므로 원인을 확인하고 새 이름을 사용하거나 관리자가 확인 후 정리한다.

복원된 DB도 같은 서버에 있으므로 이것만으로 서버 손실에 대비한 재해 복구가 완료되지는 않는다.

## 4. 복원 후 확인

최소 확인 항목:

1. 사용자·조직·멤버십과 역할이 보존되어 있는가?
2. 위치·카테고리·자산과 자산 QR 코드가 보존되어 있는가?
3. 변경 이력과 Flyway 마이그레이션 기록이 보존되어 있는가?
4. 새 레코드를 추가할 수 있는가? identity 시퀀스가 정상인가?
5. 별도의 검증 앱을 복원 DB에 연결했을 때 로그인·자산 조회·QR 접근이 동작하는가?

CI는 전체 앱 테이블의 모든 행과 Flyway 기록을 비교하고, 새 사용자 행 추가로 identity 시퀀스를 확인한다. 기존 복원 대상에 두 번째 복원을 시도해 덮어쓰기 차단과 원본 DB 불변도 확인한다. 데이터에는 비밀번호 해시가 포함되지만 비교 내용을 로그로 출력하지 않는다.

CI의 복원 검증은 앱을 복원 DB로 전환하지 않는다. 운영 복구 리허설에서는 별도 앱을 복원 DB에 연결해 사용자 흐름까지 추가 검증해야 한다.

## 5. 운영 적용 시 필요한 결정

서버가 결정되면 다음 정책을 확정하고 실제로 적용한다.

- 백업 주기: 초기안은 매일 1회와 주요 배포 전 추가 1회.
- 보관: 초기안은 일별 7일, 외부 저장소의 일별 30일. 실제 용량·보안 요구에 맞춰 조정.
- 저장 위치: 서버 내부 백업 외에 다른 서버 또는 암호화된 외부 저장소 사본 필수.
- 접근 제한: 백업 실행 계정과 복구 담당자만 읽을 수 있도록 디렉터리 권한·Windows ACL 설정.
- 전송: 암호화 통신과 외부 저장소 암호화, 접근 키 별도 관리.
- 정기 실행: Linux cron/systemd timer 또는 Windows 작업 스케줄러에 프로젝트 루트 작업 디렉터리와 Node 경로 지정.
- 실패 알림: 비정상 종료, 오래된 최신 백업, 디스크 부족과 외부 전송 실패 감지.
- 복구 리허설: 정기적으로 외부 사본을 새 DB에 복원하고 실제 소요 시간과 검증 결과 기록.

위 정책은 **초기 제안이며 자동 적용되지 않는다.** 이번 CLI는 스케줄 등록, 오래된 백업 자동 삭제, 외부 전송과 알림을 수행하지 않는다.

일일 백업만 사용하면 장애 시 최대 약 하루의 변경을 잃을 수 있다. 더 짧은 데이터 손실 허용 시간이 필요하면 주기 단축 또는 WAL 기반 복구를 별도 설계한다. 복구 시간 목표는 실제 서버 리허설 전에는 확정하지 않는다.

## 6. 장애 복구 절차

1. 장애 범위와 마지막 정상 백업 시각을 확인하고 현재 DB·볼륨을 보존한다.
2. 쓰기 요청을 중단하거나 유지보수 상태로 전환한다. 살아 있는 DB에 최신 변경이 있으면 추가 백업 확보를 시도한다.
3. 정상 백업을 별도 DB에 복원한다. 원본 DB는 그대로 둔다.
4. 복원 데이터를 검증하고, 호환되는 앱 버전을 별도 연결해 로그인·자산·QR 흐름을 점검한다.
5. 관리자 승인 후 앱의 DB 연결을 복원 DB로 변경하고 재시작한다. 이 전환은 CLI가 자동 수행하지 않는다.
6. 사용자 접근과 새 데이터 저장을 확인하고 장애 시간·복구 시간·손실 범위를 기록한다.
7. 기존 DB 정리는 검증·보관 정책 확인 후 별도로 수행한다.

`docker compose down -v`는 DB 데이터 삭제 명령이지 복구 절차가 아니다. 백업 없이 실행하지 않는다. 자동 복원 검증 스크립트도 운영 환경에서는 실행하지 않는다.

## 7. 검증과 보안

```powershell
node --test scripts/database-backup.test.mjs
```

CLI 인자 검증, 바이너리 보존, 파일 덮어쓰기 차단, 실패·잘못된 파일 정리, 복원 순서, 기존 DB 차단과 실패 시 진단 DB 보존을 검사한다.

`backups/`, `*.dump`, `*.partial`은 Git에서 제외한다. 백업은 사용자 정보와 비밀번호 해시를 포함하므로 GitHub artifact에도 업로드하지 않는다. Unix에서는 새 파일 권한을 `0600`, 새 디렉터리를 `0700`으로 요청하며 Windows에서는 별도의 NTFS ACL을 확인해야 한다.

기존 파일의 권한·암호화는 도구가 바꾸지 않는다. 백업 암호화와 외부 보관은 서버 운영 구성에서 추가해야 한다.

## 8. 공식 참고

- [PostgreSQL 16 pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html): 아카이브 복원, 단일 트랜잭션과 오류 처리.
- [PostgreSQL 16 createdb](https://www.postgresql.org/docs/16/app-createdb.html): 별도 DB 생성.
