# Assetly 결정 기록

이 문서는 Assetly를 만들면서 중요한 결정을 남기는 곳이다.

나중에 왜 이런 구조를 선택했는지 설명할 수 있도록, 기술 선택과 제품 범위 결정의 이유를 기록한다.

## 1. 프로젝트 주제

결정:

- 소규모 조직용 QR 기반 자산관리 SaaS를 만든다.

이유:

- 실제 업무 문제와 연결된다.
- 조직, 권한, 자산, 위치, 이력 등 백엔드 설계 요소가 풍부하다.
- QR 기반 현장 관리라는 차별점이 있다.
- 실제 배포 가능한 MVP 범위가 명확하다.

## 2. 프로젝트 이름

결정:

- 프로젝트명은 Assetly로 한다.

이유:

- Asset이라는 핵심 도메인이 드러난다.
- SaaS 서비스 이름처럼 짧고 기억하기 쉽다.
- 자산관리 서비스라는 인상을 준다.

주의:

- 실제 서비스명으로 확정하기 전에는 도메인, 상표, 기존 서비스 중복을 확인해야 한다.

## 3. 제품 형태

결정:

- 웹사이트가 아니라 업무용 웹 애플리케이션으로 만든다.

이유:

- 사용자는 로그인 후 자산을 관리한다.
- 랜딩 페이지보다 대시보드, 목록, 상세, 수정 화면이 중요하다.
- 실제 업무 프로그램처럼 반복 사용되는 서비스다.

## 4. SaaS 구조

결정:

- 여러 조직이 하나의 서비스에 가입해서 각자 데이터를 관리하는 멀티테넌트 SaaS 구조로 만든다.

이유:

- 단일 조직용 프로그램보다 포트폴리오 가치가 높다.
- 조직별 권한과 데이터 분리 설계를 보여줄 수 있다.
- 실제 서비스 확장 가능성이 있다.

## 5. 조직 데이터 분리 방식

결정:

- 하나의 DB에서 `organization_id`로 데이터를 분리한다.

이유:

- MVP에 적합한 단순한 구조다.
- 조직마다 DB를 따로 두는 방식은 초기 구현과 운영 비용이 크다.
- 소규모 SaaS에서는 shared database 방식으로 충분하다.

주의:

- 모든 조직 하위 리소스 조회에서 organization 조건을 빠뜨리지 않아야 한다.
- 권한 테스트를 반드시 작성한다.

## 6. QR 접근 방식

결정:

- 자산에는 QR 접근용 `public_code`를 둔다.
- QR URL은 `/a/{publicCode}` 형태로 한다.

이유:

- 조직 내부 자산번호와 외부 접근 URL을 분리할 수 있다.
- 자산번호 변경과 QR URL을 독립적으로 관리할 수 있다.
- 전체 서비스에서 유니크한 코드로 자산을 찾을 수 있다.

## 7. v1.0 범위

결정:

- v1.0에서는 회원가입, 로그인, 조직 생성, 자산 관리, 위치/카테고리 관리, QR 접근, 변경 이력까지 구현한다.

제외:

- 결제
- 실시간 알림
- 소셜 로그인
- 이미지 업로드
- Excel 입출력
- 모바일 앱
- 복잡한 통계

이유:

- 핵심 흐름을 먼저 완성하기 위해서다.
- 기능을 과하게 늘리면 배포 가능한 버전이 늦어진다.

## 8. 기술 도입 원칙

결정:

- Redis, Kafka, WebSocket, S3 같은 기술은 필요성이 생겼을 때 도입한다.

이유:

- 포트폴리오를 위해 기술을 억지로 넣으면 설명력이 떨어진다.
- 실제 문제를 해결하기 위해 도입해야 면접에서 설득력이 있다.

## 9. 인증 방식

결정:

- v1.0은 JWT 기반 인증으로 시작한다.

이유:

- 프론트엔드와 백엔드가 분리된 구조에 잘 맞는다.
- Spring Security와 함께 인증/인가 구현 경험을 보여줄 수 있다.

추후 검토:

- refresh token
- token rotation
- OAuth 로그인

## 10. 변경 이력

결정:

- 자산의 중요한 변경은 `asset_histories`에 기록한다.

이유:

- 자산관리 서비스에서는 현재 상태뿐 아니라 변경 과정이 중요하다.
- "누가, 언제, 무엇을 바꿨는가"를 확인할 수 있어야 한다.
- 감사 로그와 운영 신뢰성을 보여줄 수 있다.

## 11. 프론트엔드 UX 원칙

결정:

- 마케팅 랜딩보다 실제 업무 화면을 우선한다.
- 통계 카드 나열과 설명용 장식처럼 전형적인 템플릿 구성을 피한다.
- 실제 API 데이터가 아닌 조직, 자산, 활동 내역을 화면에 표시하지 않는다.
- 아직 구현되지 않은 기능을 동작하는 버튼이나 메뉴처럼 노출하지 않는다.
- 자산관리 도구에 맞는 높은 정보 밀도, 명확한 표 구조, 절제된 색과 각진 컨트롤을 사용한다.

이유:

- 사용자가 반복적으로 사용하는 운영 도구는 장식보다 탐색 속도와 데이터 신뢰성이 중요하다.
- 가짜 데이터와 동작하지 않는 컨트롤은 제품 완성도를 오해하게 하고 테스트도 어렵게 만든다.
- 프로젝트 고유의 업무 흐름이 보여야 범용 템플릿처럼 보이지 않는다.

## 12. 데이터베이스 스키마 변경 방식

결정:

- 운영과 로컬 PostgreSQL의 스키마 변경은 Flyway 마이그레이션으로 관리한다.
- Hibernate `ddl-auto`는 `validate`로 두고 애플리케이션이 스키마를 자동 변경하지 않게 한다.
- H2 테스트 환경도 운영과 같은 마이그레이션 파일을 적용한다.

이유:

- 배포 시 어떤 스키마 변경이 어떤 순서로 적용됐는지 추적할 수 있다.
- 엔티티 변경만으로 운영 DB가 예기치 않게 수정되는 것을 막는다.
- 테스트에서 마이그레이션 SQL과 JPA 엔티티의 불일치를 조기에 발견할 수 있다.

주의:

- 이미 적용된 마이그레이션 파일은 수정하지 않고 새 버전 파일을 추가한다.
- 현재 개발 PC에는 Docker가 없어 PostgreSQL 컨테이너 실행은 별도 환경에서 검증해야 한다.

## 13. 멤버 관리 권한 정책

결정:

- v1.0에서는 이메일 발송 초대 대신 이미 가입된 사용자를 이메일로 조직에 추가한다.
- Owner는 모든 역할을 추가·변경·제거할 수 있다.
- Admin은 Manager와 Member만 추가·변경·제거할 수 있다.
- 조직에는 항상 Owner가 한 명 이상 남아 있어야 한다.
- 실제 이메일 초대와 가입 대기 상태는 v1.1 이후 후보로 둔다.

이유:

- 이메일 인프라 없이도 여러 사용자가 함께 조직을 운영하는 핵심 흐름을 완성할 수 있다.
- Admin이 자신이나 다른 사용자를 상위 역할로 승격하는 권한 상승을 방지한다.
- 마지막 Owner 보호로 조직 관리 권한이 사라지는 상태를 막는다.

## 14. 위치와 카테고리 관리 정책

결정:

- 위치와 카테고리는 조직별 데이터로 분리하고 이름도 조직 안에서만 유일하게 관리한다.
- 모든 조직 멤버가 목록을 조회할 수 있고 Owner와 Admin만 생성·수정·삭제할 수 있다.
- 이름과 설명의 앞뒤 공백은 저장 전에 제거한다.
- 자산 테이블이 연결되는 단계에서 사용 중인 위치와 카테고리의 삭제를 차단한다.

이유:

- 자산 등록 전에 기준 정보를 먼저 준비할 수 있어야 한다.
- Manager와 Member도 자산 조회·수정 과정에서 기준 정보 목록이 필요하다.
- 조직 ID와 리소스 ID를 함께 조회해 다른 조직의 기준 정보 조작을 방지한다.

## 15. 자산 식별자와 삭제 정책

결정:

- `assetCode`는 앞뒤 공백을 제거하고 대문자로 저장하며 조직 안에서 유일하다.
- QR 접근에 사용할 `publicCode`는 자산 생성 시 무작위로 발급하고 전체 서비스에서 유일하다.
- 자산 삭제 API는 물리 삭제 대신 `deleted_at`을 기록하는 비활성화로 처리한다.
- Owner와 Admin은 전체 정보를, Manager는 상태·위치·담당자만 수정한다.
- 비활성화되지 않은 자산이 참조하는 위치와 카테고리는 삭제할 수 없다.

이유:

- 내부 관리번호와 외부 접근 식별자를 분리하면 URL 안정성과 보안이 좋아진다.
- 비활성화는 이후 변경 이력과 감사 흐름을 보존할 수 있다.
- Manager의 현장 업무 범위를 허용하면서 구매 정보와 분류 체계 변경은 제한한다.

## 16. 변경 이력과 QR 접근 정책

결정:

- 자산 생성과 비활성화는 작업 단위로 한 건을 기록한다.
- 수정은 실제 값이 달라진 필드마다 한 건을 기록하며 상태·위치·담당자는 전용 작업 종류를 사용한다.
- 비활성화된 자산도 조직 감사 이력에서는 조회할 수 있다.
- `publicCode` URL은 식별자만 공개하며 자산 데이터 조회에는 로그인과 조직 멤버십이 필요하다.
- QR URL로 로그인 화면에 이동할 때 `next` 쿼리로 원래 경로를 보존한다.

이유:

- 필드별 기록은 변경 원인을 빠르게 파악할 수 있고 화면에서도 전후 값을 명확히 보여줄 수 있다.
- 공개 코드가 인증을 대신하지 않게 해 URL 유출 시에도 조직 데이터를 보호한다.
- 비활성화 이후에도 감사 기록을 보존해야 운영 이력을 신뢰할 수 있다.

## 17. 활성 조직 선택 정책

결정:

- 사용자의 마지막 활성 조직 ID를 브라우저 로컬 저장소에 보관한다.
- 저장된 조직이 현재 소속 조직 목록에 없으면 목록의 첫 조직으로 안전하게 대체한다.
- 로그아웃 시 토큰과 활성 조직 ID를 함께 제거한다.
- QR 자산 조회가 성공하면 해당 자산의 조직을 활성 조직으로 지정한다.
- 멤버 관리 화면에서 권한이 없는 조직으로 전환하면 대시보드로 이동한다.

이유:

- 새로고침과 재로그인 후에도 업무 맥락을 유지할 수 있다.
- 탈퇴나 권한 변경으로 유효하지 않은 조직 ID가 남아도 접근 오류에 갇히지 않는다.
- QR 현장 작업 후 일반 워크스페이스로 돌아갈 때 다른 조직 데이터가 보이는 혼선을 막는다.

## 18. 운영 컨테이너와 네트워크 정책

결정:

- 백엔드는 Java 21, 프론트엔드는 Node.js 22 멀티스테이지 이미지로 빌드한다.
- 최종 이미지에서는 빌드 도구를 제외하고 비루트 사용자로 프로세스를 실행한다.
- 외부 요청은 프론트엔드만 받고 `/api` 요청을 내부 백엔드 주소로 전달한다.
- PostgreSQL은 Compose 내부 네트워크에서 접근하고 호스트 포트는 로컬 주소에만 바인딩한다.
- PostgreSQL readiness, 백엔드 DB readiness와 프론트엔드 HTTP healthcheck 순서로 서비스를 시작한다.
- 운영 프로필에서는 환경변수 없는 DB 연결과 예시 JWT 키를 허용하지 않는다.

이유:

- 빌드 환경과 실행 환경을 분리하면 이미지 크기와 공격 표면을 줄일 수 있다.
- 브라우저가 백엔드 내부 주소를 알 필요가 없어 배포 환경에 따라 `BACKEND_URL`만 바꾸면 된다.
- 준비되지 않은 DB나 백엔드에 다음 서비스가 연결되는 시작 순서 문제를 줄인다.
- 개발 편의를 위한 기본 비밀값이 운영에 그대로 사용되는 사고를 시작 단계에서 차단한다.

## 19. 지속적 통합 정책

결정:

- `main` push와 모든 Pull Request에서 백엔드 테스트와 프론트엔드 검사·빌드를 실행한다.
- 두 기본 검사가 통과한 뒤 실제 백엔드와 프론트엔드를 실행해 Playwright 핵심 흐름을 검증한다.
- CI 백엔드는 H2 로컬 프로필을 사용해 외부 DB나 저장소 비밀값 없이 격리한다.
- 워크플로 권한은 저장소 읽기로 제한하고 같은 브랜치의 오래된 실행은 자동 취소한다.
- 브라우저 테스트 로그와 실패 자료는 7일 후 자동 삭제한다.

이유:

- 빠른 단위 검사와 상대적으로 느린 브라우저 검사를 분리해 실패 지점을 바로 확인할 수 있다.
- Pull Request 단계에서 실제 사용자 흐름의 회귀를 막고 `main` 브랜치 상태를 항상 검증한다.
- 외부 인프라 의존성을 제거하면 포크 Pull Request에도 비밀값을 노출하지 않고 동일한 검사를 실행할 수 있다.
- 보관 기간을 제한하면 문제 분석 자료는 확보하면서 artifact 사용량이 계속 누적되는 것을 막는다.

## 20. 운영 컨테이너 검증 정책

결정:

- 기본 검사 통과 후 실제 Dockerfile과 Compose로 운영 프로필·PostgreSQL 16 환경을 실행한다.
- 서비스 healthy 상태 확인, 컨테이너 재생성 후 데이터 유지, 전체 Playwright 흐름을 각각 검증한다.
- H2 기반 검증과 PostgreSQL 기반 검증은 독립 job으로 유지한다.
- CI 실행별 프로젝트와 임시 비밀값을 사용하고 해당 실행의 컨테이너·볼륨만 종료 시 정리한다.
- 컨테이너 내부 healthcheck 주소는 IPv4 루프백을 명시한다.

이유:

- 로컬 PC에 Docker가 없어도 실제 배포 이미지와 DB 조합의 결함을 원격 CI에서 찾을 수 있다.
- 인메모리 DB로 확인할 수 없는 마이그레이션 호환성과 영속 볼륨 동작을 검증한다.
- 컨테이너 교체 후에도 사용자와 자산 데이터가 유지되는지 배포 전에 확인한다.

## 21. DB 백업과 복원 안전 정책

결정(2026-10-11):

- 서버·도메인이 미정이므로 서버별 배포 설정에 앞서 DB 백업·복원 기반을 추가한다.
- 컨테이너 내부 `pg_dump`의 custom 아카이브를 Node.js 바이너리 스트림으로 저장한다.
- 완성된 백업만 게시하고 기존 파일 덮어쓰기와 Git 업로드를 차단한다.
- 복원은 새 `assetly_restore_*` DB만 허용하며 원본 DB와 앱 연결은 변경하지 않는다.
- 단일 트랜잭션 복원과 오류 중단을 사용하고 실패한 새 DB는 진단용으로 남긴다.
- 안전성 단위 테스트와 CI의 실제 PostgreSQL 전체 행·이력·Flyway 기록 비교, 시퀀스 및 기존 DB 보호 검증을 추가한다.
- 운영 정기 스케줄, 외부 보관·암호화와 앱 전환 복구 리허설은 서버 선정 후 구성한다.

이유:

- 영속 볼륨 검증은 서버나 볼륨 손실에 대비한 백업을 대신하지 않는다.
- 복원을 원본 DB와 분리하면 검증 과정에서 운영 데이터를 덮어쓰는 사고를 줄일 수 있다.
- 바이너리 스트림 저장은 Windows 셸의 텍스트 인코딩에 따른 아카이브 손상을 피한다.
- CI에서 생성한 DB 백업은 개인정보 성격의 데이터를 포함하므로 artifact로 공개하지 않는다.

검증 결과:

- [GitHub Actions 실행](https://github.com/wnsgh1a/assetly/actions/runs/38110363669), 코드 커밋 `b032fbc`의 네 작업 모두 성공.
- 안전성 테스트 13개와 실제 PostgreSQL 큰 아카이브 백업·복원 검증 통과.
- 모든 앱 테이블·Flyway 기록 일치, 원본 불변, 기존 대상 보호와 identity 시퀀스 확인.
- 백엔드 58개 및 H2·PostgreSQL 브라우저 각각 8개 통과·4개 조건부 제외. 운영 서버의 정기 백업·외부 보관·앱 전환은 여전히 미설정.

## 22. 포트폴리오 우선·최저 예산 배포 정책

결정(2026-10-12):

- 포트폴리오가 본질이며 실제 사용자는 추가 검증 기회로 취급한다. 상용 서비스 규모로 확장하지 않는다.
- 호스팅 월 0원을 우선 목표로 하며 사용자 승인 없이 유료 전환·구매·과금 자원을 만들지 않는다.
- 서버 1대에 기존 Docker 구성을 올리는 무료 배포를 우선 검토한다. Oracle Always Free는 후보일 뿐 아직 선정·가입·생성하지 않았다.
- 무료 서버 확보가 어려우면 임시 시연·영상으로 대체한다. 무료 체험 만료 후 유료 전환을 기본 경로로 삼지 않는다.
- 임시 터널은 상시 운영의 대체재가 아니며 실제 데이터 보관용으로 안내하지 않는다.
- 현재 남은 실제 배포 단계에는 공급자 한도 확인, ARM 이미지 호환 검증(ARM 서버 선택 시), HTTPS 주소, 비밀값과 외부 백업 구성이 포함된다.

검토 근거(2026-10-12 공식 문서 확인):

- [Oracle Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): A1 무료 계정 기준 총 2 OCPU·12 GB, 홈 리전·스토리지 한도 확인 필요. 용량 부족과 유휴 인스턴스 회수 가능.
- [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/): 임시 주소 기반 테스트·시연용이며 상시 운영용으로 간주하지 않는다.
- [Render 무료 운영 제한](https://render.com/docs/free): 무료 PostgreSQL은 30일 만료이므로 현재 영속 DB의 장기 운영 대안으로 그대로 채택하지 않는다.

## 23. 배포 제외 v1 화면 마감

결정(2026-10-18):

- 사용자 요청에 따라 배포 작업을 제외하고 v1의 화면·오류 복구·핵심 브라우저 회귀를 마무리한다.
- 조회 실패를 자산 0개·빈 이력으로 표시하지 않고 재시도 경로를 제공한다.
- 자산 옵션 조회 실패 시 저장을 막아 조회 오류 상태의 잘못된 저장을 방지한다.
- 자산 상세는 조직·자산 조합별로 상태를 분리하며, 필터 요청과 탭 조회는 오래된 요청을 취소한다.
- 자산별 이력 조회를 상세·QR 화면에서 공유하고 페이지 이동을 제공한다.
- 인증 만료는 현재 토큰과 일치하는 요청만 세션 만료 이벤트를 발생시키고 원래 경로로 로그인 복귀한다.
- 기존 디자인을 유지하면서 태블릿 필터·QR 배치와 긴 텍스트·버튼 축소 문제를 수정한다.
- 테스트·스크린샷은 로컬 H2 데이터로 수행한다. 실제 서버·키·클라우드 자원은 변경하지 않는다.

로컬 검증: ESLint·production build 성공, Playwright 27개 통과·5개 조건부 제외. 실제 배포와 운영 자동화는 별도 미완료 상태로 유지한다.
