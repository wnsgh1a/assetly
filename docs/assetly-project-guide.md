# Assetly 프로젝트 진행 가이드

이 문서는 Assetly를 만들 때 계속 참고할 기준 문서다.

제품 기획서가 "무엇을 만들 것인가"를 정리한다면, 이 문서는 "어떤 태도로, 어떤 순서로, 어디까지 만들 것인가"를 정리한다.

Assetly를 개발하다 보면 기능을 더 넣고 싶어지거나, 기술 스택을 과하게 확장하고 싶어질 수 있다. 그럴 때 이 문서를 기준으로 방향을 다시 맞춘다.

## 1. 프로젝트 정체성

Assetly는 단순한 CRUD 연습 프로젝트가 아니다.

목표는 다음과 같다.

> 실제 사용 가능한 소규모 자산관리 SaaS를 기획, 설계, 개발, 배포, 운영해보는 것.

그래서 코드를 빨리 많이 작성하는 것보다, 실제 서비스처럼 필요한 과정을 밟는 것이 중요하다.

Assetly는 다음 특징을 가진다.

- 웹사이트가 아니라 업무용 웹 애플리케이션이다.
- 단일 조직용 프로그램이 아니라 여러 조직이 각자 가입해서 쓰는 SaaS다.
- 단순 자산 목록이 아니라 QR 기반 현장 관리 흐름을 핵심 가치로 둔다.
- 모든 중요한 변경은 이력으로 남긴다.
- 권한에 따라 할 수 있는 작업이 달라진다.
- 최종적으로 실제 배포와 운영까지 목표로 한다.

## 2. 한 문장으로 설명하기

Assetly는 소규모 조직이 자산에 QR을 붙이고, 현장에서 스캔해 위치, 상태, 담당자, 변경 이력을 관리하는 자산관리 SaaS다.

## 3. 이 프로젝트로 보여주고 싶은 역량

Assetly는 포트폴리오에서 다음 역량을 보여주기 위한 프로젝트다.

- 실제 문제를 제품으로 바꾸는 기획력
- 멀티테넌트 SaaS 구조 이해
- 인증과 권한 처리
- 조직, 멤버, 역할 기반 데이터 설계
- REST API 설계
- 관계형 DB 모델링
- 변경 이력과 감사 로그 설계
- QR 기반 업무 흐름 구현
- 프론트엔드와 백엔드 연동
- Docker 기반 개발 환경 구성
- 테스트 코드 작성
- CI/CD 구성
- 실제 서버 배포와 운영 경험

중요한 것은 "Spring Boot로 게시판을 만들었다"가 아니라, "작은 서비스 하나를 실제 사용 가능하게 설계하고 운영했다"라고 말할 수 있는 결과물을 만드는 것이다.

## 4. 왜 Assetly인가

자산관리 문제는 실제 업무에서 자주 발생한다.

예를 들어 다음과 같은 상황이다.

- 노트북이 어디 있는지 모른다.
- 장비를 누가 쓰고 있는지 모른다.
- 마지막 점검일이 기록되어 있지 않다.
- 사진은 폴더에 있고, 위치는 엑셀에 있고, 담당자는 메신저에 남아 있다.
- 현장에서 확인한 내용을 나중에 다시 수기로 입력해야 한다.

Assetly는 이 문제를 QR 기반 흐름으로 해결한다.

1. 자산을 등록한다.
2. QR을 발급한다.
3. 자산에 QR을 붙인다.
4. 현장에서 QR을 스캔한다.
5. 자산 정보를 확인한다.
6. 위치, 상태, 담당자, 점검 내용을 바로 갱신한다.
7. 변경 이력이 자동으로 남는다.

이 흐름이 Assetly의 핵심이다.

## 5. 가장 중요한 제품 원칙

### 원칙 1. MVP를 먼저 완성한다

처음부터 모든 기능을 넣지 않는다.

v1.0은 다음 흐름이 실제로 돌아가면 성공이다.

회원가입 → 로그인 → 조직 생성 → 자산 등록 → QR 발급 → QR 스캔 → 자산 상세 확인 → 자산 수정 → 변경 이력 기록

이 흐름이 완성되기 전까지는 부가 기능을 늘리지 않는다.

### 원칙 2. 기술은 문제를 해결할 때 도입한다

Redis, Kafka, WebSocket, S3, OAuth 같은 기술은 멋있어 보이지만 처음부터 필요하지 않을 수 있다.

Assetly에서는 다음 기준으로 기술을 도입한다.

- 지금 실제 문제가 있는가?
- 이 기술이 그 문제를 명확히 해결하는가?
- 도입 후 설명할 수 있는 이유가 있는가?

예를 들어 이미지 업로드가 필요해지면 S3 호환 스토리지를 도입할 수 있다.
알림이 복잡해지면 Redis나 메시지 큐를 검토할 수 있다.

반대로 이유 없이 기술을 추가하지 않는다.

### 원칙 3. 업무 프로그램처럼 만든다

Assetly는 예쁜 랜딩 페이지가 중심인 서비스가 아니다.

중요한 것은 다음이다.

- 자산을 빠르게 찾을 수 있어야 한다.
- 상세 정보를 한눈에 볼 수 있어야 한다.
- 수정 흐름이 명확해야 한다.
- 모바일에서 QR 스캔 후 바로 처리할 수 있어야 한다.
- 관리자는 대시보드에서 현재 상태를 파악할 수 있어야 한다.

디자인은 화려함보다 명확함, 일관성, 업무 효율성을 우선한다.

### 원칙 4. 모든 데이터는 조직 단위로 분리한다

Assetly는 SaaS이기 때문에 여러 조직이 함께 사용하는 구조다.

따라서 거의 모든 주요 데이터는 `organizationId`를 기준으로 분리된다.

- A 회사 사용자는 A 회사 자산만 봐야 한다.
- B 연구실 사용자는 B 연구실 자산만 봐야 한다.
- 같은 사용자가 여러 조직에 속할 수 있어야 한다.
- 사용자의 권한은 조직마다 다를 수 있다.

이 원칙은 DB 설계, API 설계, 권한 처리에서 계속 지켜야 한다.

### 원칙 5. 변경 이력을 남긴다

자산관리에서 중요한 것은 현재 상태뿐만이 아니다.

"언제, 누가, 무엇을 바꿨는가"가 중요하다.

따라서 다음 작업은 이력으로 남긴다.

- 자산 등록
- 자산 정보 수정
- 위치 변경
- 담당자 변경
- 상태 변경
- 대여
- 반납
- 점검
- 삭제 또는 비활성화

v1.0에서는 모든 종류를 완벽히 구현하지 않더라도, 변경 이력을 남기는 구조는 처음부터 설계한다.

## 6. 개발 진행 순서

Assetly는 다음 순서로 진행한다.

1. 제품 방향 정리
2. 화면 흐름 설계
3. DB 모델 설계
4. API 명세 작성
5. 백엔드 프로젝트 생성
6. 프론트엔드 프로젝트 생성
7. Docker 개발 환경 구성
8. 인증 구현
9. 조직과 멤버 구현
10. 자산, 위치, 카테고리 구현
11. 변경 이력 구현
12. QR 발급과 QR 접근 구현
13. 기본 UI 구현
14. 테스트 코드 작성
15. CI/CD 구성
16. 운영 배포
17. 사용해보고 피드백 반영

이 순서를 무조건 기계적으로 지킬 필요는 없지만, 큰 흐름은 유지한다.

## 7. v1.0에서 꼭 완성해야 하는 흐름

v1.0의 성공 기준은 기능 개수가 아니라 실제 사용 흐름이다.

### 관리자 흐름

1. 회원가입한다.
2. 로그인한다.
3. 조직을 만든다.
4. 위치를 등록한다.
5. 카테고리를 등록한다.
6. 자산을 등록한다.
7. QR을 확인한다.
8. 자산 상세를 조회한다.
9. 자산 정보를 수정한다.
10. 변경 이력을 확인한다.

### 현장 사용자 흐름

1. QR을 스캔한다.
2. 자산 상세 페이지에 접근한다.
3. 로그인한다.
4. 자산 정보를 확인한다.
5. 권한이 있으면 위치나 상태를 수정한다.
6. 수정 내용이 이력에 남는다.

이 두 흐름이 돌아가면 v1.0의 뼈대는 성공이다.

## 8. v1.0에서 하지 않을 것

프로젝트가 중간에 커지는 것을 막기 위해 v1.0에서 하지 않을 일을 명확히 둔다.

- 결제 기능
- 실시간 채팅
- 복잡한 통계
- 모바일 네이티브 앱
- Kafka
- Redis 기반 고도화
- 소셜 로그인
- 조직별 요금제
- 대량 Excel 가져오기
- 대량 QR 라벨 출력
- 관리자용 슈퍼 어드민
- 멋진 마케팅 랜딩 페이지

이 기능들은 좋은 기능일 수 있지만 v1.0 목표는 아니다.

## 10. Codex와 작업할 때의 기준

Codex는 작업할 때 다음 기준을 따른다.

1. 먼저 관련 문서를 읽고 현재 방향을 확인한다.
2. 새 기능을 만들기 전에 MVP 범위에 맞는지 확인한다.
3. 기존 설계와 충돌하면 설계를 먼저 업데이트한다.
4. 기능 구현 시 DB, API, 화면 흐름이 서로 맞는지 확인한다.
5. 임시 구현으로 끝내지 않고 테스트 가능한 상태를 목표로 한다.
6. 사용자 경험이 불편하면 기능이 동작해도 개선 대상으로 본다.
7. 과한 기술 도입은 피하고, 도입 이유를 문서에 남긴다.

즉, 이 프로젝트에서는 "일단 되는 코드"보다 "서비스로 이어질 수 있는 구조"를 우선한다.
